# Люмен — вымышленная веб-ОС

Вымышленная операционная система «Люмен» в браузере. Названия, ядро и оболочка придуманы.

## Запуск

```bash
./serve.sh 12000     # затем открыть http://localhost:12000/
```

`serve.sh` поднимает `server.py` — он отдаёт файлы проекта, работает прокси
`/__proxy` и держит живой Chromium для приложения «Браузер» через `/__live`.
Простой `python3 -m http.server` тоже покажет систему, но окно браузера в нём
не заработает: ему нужен сервер.

## Структура

| Файл | Назначение |
| --- | --- |
| `index.html` | Каркас оболочки: загрузка, локскрин, рабочий стол, панель задач, «Пуск», виджеты, быстрые параметры, контекстное меню, SVG-спрайт логотипа |
| `styles.css` | Дизайн-система: токены тем, стекло, обои, окна, все приложения |
| `os.js` | Ядро: иконки, состояние, VFS, оконный менеджер, приложения, оболочка |
| `server.py` | Сервер и прокси `/__proxy` для браузера, живой Chromium через `/__live` |
| `e2e.html` | Автотесты системы |

## Архитектура os.js (порядок важен)

Файл — один IIFE-набор модулей, порядок объявления критичен:

1. `ICO` — SVG-иконки
2. `State` — глобальное состояние (тема, акцент, обои, `open`, `zTop`)
3. `Sound` — синтез сигналов через Web Audio API
4. `VFS` — виртуальная файловая система (`C:` в памяти)
5. `Notify` — тосты
6. `WM` — оконный менеджер (`WM.register` / `WM.open`); `Apps` заполняется через `WM.register`
7. `openCtx` — контекстные меню
8. Приложения: `explorer`, `notepad`, `terminal`, `calc`, `taskmgr`, `photos`, `viewer`, `paint`, `music`, `calendar`, `mail`, `store`, `security`, `settings`
9. `WALLS`, `ACCENTS`, `applyAccent/Theme/Wall/Transparency/Align`
10. `TaskMan` — список процессов (данные для терминала и диспетчера)
11. Оболочка: `renderIcons`, `renderTaskbar`, `StartMenu`, `Widgets`, `Quick`, `Spot`, `HUD`, `initKeys`
12. `init()` — точка входа; вызывается на `DOMContentLoaded`

## Приложение: как добавить

```js
WM.register({
  id: 'myapp', title: 'Имя', icon: ICO.settings, w: 700, h: 480,
  init(rec, arg) { rec.body.innerHTML = '...'; rec.api.что_угодно = fn; },
  onClose(rec) { clearInterval(rec.api.iv); },
});
```

Затем добавить id в `PINNED` (панель задач) или `DESK` (значки рабочего стола).
`rec.api` — публичный интерфейс окна (используется, например, `rec.api.run` терминала).

## Соглашения

- Комментарии и UI-тексты на русском, идентификаторы кода — латиницей.
- Строки HTML собираются конкатенацией, а не шаблонными литералами (осознанный выбор: упрощает вставку больших блоков).
- Пользовательский ввод всегда проходит через `esc()` перед вставкой в разметку.
- Интервалы окон хранятся в `rec.api.iv` и чистятся в `onClose`, иначе утечка таймеров.
- Настройки сохраняются в `localStorage` под префиксом `w12.` (`save()` в блоке оформления).

## Проверка изменений

```bash
node --check os.js
```

Затем открой страницу и проверь: загрузка → локскрин → терминал (`neofetch`/`help`) →
перетаскивание и снап окна → смена темы и обоев.

### Автоматическая проверка (e2e.html)

`e2e.html` открывает систему в iframe, нажимает «Войти» и проверяет реальную
видимость через накопленную `opacity` по цепочке предков, затем открывает все
14 приложений и читает вывод терминала. Полагаться на один лишь текст в DOM
нельзя: скрытый контент всё равно присутствует в разметке.

```bash
python3 -m http.server 12000 &
chromium --headless --disable-gpu --no-sandbox \
  --virtual-time-budget=25000 --dump-dom http://localhost:12000/e2e.html
```

Ожидаемая последняя строка: `ИТОГ: рабочий стол виден; все 14 приложений видны`.

Две ловушки при проверке:

- В headless-режиме CSS-транзишены замирают на `currentTime=0`, поэтому
  вычисленная `opacity` остаётся стартовой. Тест отключает анимации перед замером.
- `const WM` внутри скрипта не попадает в `window` (лексическая область видимости),
  поэтому из iframe доступ идёт через `w.eval('WM.open(...)')`.

## Известные грабли

- `#desk` в CSS имеет `opacity:0` и проявляется только с классом `.on`. Если после
  входа чёрный экран — проверь, что `revealDesk()` вызывается. Именно эта строка
  однажды потерялась при сборке `os.js`, и симптом был «висит чёрный экран».

- Тесты через `--virtual-time-budget` искажают загрузку внешних сайтов и
  срабатывание `onload`: рамка может показаться пустой, хотя сайт открылся.
  Проверять браузер нужно в реальном времени (CDP или обычный браузер).

- Прокси снимает `integrity` у тегов. Если этого не делать, браузер отбрасывает
  скрипты и стили, и страница приходит «лысой».

- `localhost` и частные сети в прокси закрыты намеренно. Открывать их нельзя:
  прокси доступен из интернета и иначе станет средством хода во внутреннюю сеть.

## Рабочий стол: созданные папки и файлы

Правый клик по свободному месту рабочего стола → «Создать папку» / «Создать
текстовый файл». Пункты идут первыми в меню.

Как это устроено:

- Созданное живёт в виртуальной ФС по пути `C:\Users\<имя>\Рабочий стол`
  (`DESK_DIR`), поэтому автоматически видно в Проводнике и в терминале.
- Список значков (`deskItems`) хранится в `localStorage` под ключом
  `lumen.deskItems.<имя>`. При загрузке `loadDeskItems()` заново поднимает
  элементы в ФС, чтобы после перезагрузки значки не пропадали. У каждой
  учётной записи свой список и свой рабочий стол.
- `renderIcons()` рисует сначала созданное пользователем, затем системные
  значки из `DESK`.
- Имена не конфликтуют: `freeName()` подбирает «Новая папка», «Новая папка (2)», …
- Переименование копирует содержимое каталога (`deepCopy`) и удаляет исходный.
- `#icons` прокручивается по вертикали: без этого при большом числе значков
  нижний ряд уходил под панель задач и был недоступен.

## Панель администратора

Раздел «Панель администратора» в Параметрах. Открывается кодом владельца,
который владелец задал сам при первом запуске. Если код не задан, панель
открывается без проверки и сама предлагает задать код.

- Неверный код → «Вы не владелец. Вам недоступно. Введите правильный код.»,
  счётчик неудачных попыток растёт, поле очищается, панель не открывается.
- Верный код → доступ открыт, счётчик сбрасывается, запись в журнал.
- Вход работает кнопкой и клавишей Enter.

Внутри восемь разделов (`ADM_TABS`), переключаемых чипами:

| Раздел | Что делает |
|---|---|
| Обзор | состояние, нагрузка, быстрые действия |
| Пользователи | список учётных записей, добавление, пароль, роль, удаление |
| Имя системы | правка имени, версии, ядра, сборки, пользователя |
| Окна | список открытых окон, показать/закрыть, сетка/каскад/свернуть/закрыть все |
| Оформление | тема, акцент, обои, прозрачность, яркость, громкость |
| Файлы | счётчики, выгрузка отчёта, очистка стола, восстановление ФС |
| Питание | код владельца, текущий сеанс, режим оформления, блокировка, спящий режим, перезапуск, выключение, выход |
| Журнал | все записи, очистка |

Все действия настоящие: окна закрываются через `WM.close`, очистка стола — через
`VFS.rm` + `saveDeskItems`, восстановление ФС — через `VFS.restore`, питание — через
`power()`. Состояние в `State.admin` / `adminAttempts` / `adminLog`. Это
художественный концепт, а не защита: код лежит в исходнике открытым текстом.

## Имя системы

Единый источник — модуль `SysInfo` в `os.js`. Поля: `name`, `version`, `kernel`,
`build`, `user`; хранятся в localStorage под ключом `w12.sysinfo`.

Всё, что должно показывать эти значения, помечается в разметке атрибутом
`data-sys="name|namever|version|kernel|build|user|user-initial"`. После правки
достаточно вызвать `SysInfo.apply()` — он обновит все узлы, включая заголовок
вкладки. `SysInfo.update({...})` сохраняет и применяет, `SysInfo.reset()`
возвращает исходные значения.

Сейчас метки стоят на загрузочном экране, экране входа, аватаре, «Пуске», ленте
виджетов и в «О системе». Терминал (`ver`, `neofetch`) и отчёт администратора
берут значения через `SysInfo.get()`.

Исходные значения: Люмен 1.4, ядро `люмен-1.4-generic`, сборка 3040,
пользователь «Степан».

## Включение компьютера и учётные записи

Цепочка запуска: системный блок → кнопка питания → **имя учётной записи и
пароль** → монитор → загрузка → рабочий стол.

Кнопки «Пропустить» нет намеренно: включить компьютер можно только кнопкой
питания (или Enter/пробелом). Не добавляйте её обратно.

Паролей в исходниках нет. Ни одного. Не добавляйте их обратно: это личные
данные владельца, а репозиторий публичный.

## Доступ: учётные записи, код владельца и восстановление

Модуль `Auth` в начале `os.js` — это SHA-256 на чистом JS. Он проверен против
эталона Node (`crypto.createHash('sha256')`) на 14 наборах, включая пустую
строку, кириллицу и тексты длиной 55/56/63/64/1000/5000 знаков: совпадение
полное. Если будете править — прогоните такую же сверку.

### Код владельца

Система хранит только отпечаток: `{salt, iter, hash}`, где `hash` — результат
`iter` повторов SHA-256 от `salt + ':' + текст`. Соль случайная на каждый
отпечаток, повторов 12 000. Обратно в код отпечаток не превращается, поэтому
подсмотреть код нельзя ни в файлах, ни в хранилище браузера.

Проверка сравнения — без раннего выхода: по времени ответа нельзя понять, где
ошибка.

Код владельца — главный ключ системы: он открывает панель администратора и
позволяет задать новый пароль любой учётной записи.

Хранилище кода: ключ `w12.auth`. Старые ключи `w12.lockcode`, `w12.userpass` и
поле `pass` в `w12.auth` больше не используются — в них лежал открытый текст или
отпечаток отдельного пароля. При загрузке `loadPrefs()` снимает устаревшее поле
`pass`, если оно осталось от прежней версии.

### Учётные записи

Модуль `Users` держит список учётных записей в ключе `w12.users`. У каждой
записи: имя, роль (`admin` или `user`) и шифрованная часть.

**Пароль не хранится вообще** — ни открытым текстом, ни отпечатком. Функция
`Auth.seal(payload, пароль)` выводит из пароля ключ (`stretch` — те же 12 000
повторов SHA-256 с солью) и шифрует им запись; `Auth.open(rec, пароль)`
расшифровывает её и проверяет метку целостности (`tag`). Верный пароль
возвращает запись, неверный — `null`.

Формат записи: `{name, role, salt, iter, ct, tag}`. Имя и роль лежат открыто:
имя и так показано на экране входа, а без него запись не найти по введённому
имени. Роль продублирована внутри шифрованной части, и `Users.verify()`
сверяет её с открытой. Поэтому подменить роль правкой хранилища не выйдет:
метка не сойдётся, и вход не пройдёт.

Важно про смену роли: роль внутри шифрованной части нельзя перешить без
пароля. Поэтому `Users.setRole()` требует новый пароль и перешивает запись
целиком. Не пытайтесь менять `rec.role` напрямую — вход после этого перестанет
работать.

Начальных записей нет: `Users.DEFAULTS` пуст. Пароля по умолчанию в системе не
существует — владелец заводит первую учётную запись сам на экране первого
запуска (`paintFirstRun()`), и она получает роль администратора.

Последнего администратора удалить и понизить нельзя: панель администратора
осталась бы без доступа.

### Поток входа

1. **Первый запуск** (`isFirstRun()`) — `paintFirstRun()`: имя владельца, пароль
   и повтор. Там же необязательное поле кода владельца: если код не задать,
   забытый пароль восстановить будет нечем. `Users.add(имя, пароль, 'admin')`
   создаёт первую запись.
2. **Экран включения** — `paintLogin()`: поле имени (подставлено из
   `w12.lastuser`) и поле пароля. `tryPass()` сверяет пару через
   `Users.verify()`.
3. **Экран блокировки** (`#lock.needcode`) — просит пароль текущей учётной
   записи (`currentUser()`), а не код владельца.
4. После входа `applyCurrentUser()` пересчитывает всё, что зависит от имени:
   домашнюю папку, рабочий стол, значки, панель задач.

`needGate()` всегда истинна: без учётной записи в систему не попасть. Код
владельца — не отдельный вход, а ключ к панели администратора и к сбросу
пароля.

Экран включения — единственная проверка при старте. После него экран входа
не показывается: `bootSequence()` сразу вызывает `revealDesk()`. Поэтому
дважды ничего вводить не нужно.

### Забыли пароль

Ссылка «Забыли пароль?» есть на обоих экранах: `openRecovery()` на блокировке и
`forgotOnBoot()` на включении. Оба ведут к коду владельца, а он — к заданию
нового пароля:

- `forgotOnBoot()` → `paintChooseUser()` (если записей больше одной) →
  `paintResetPass()` → `Users.setPassword()`;
- `openRecovery()` → `checkOwnerCode()` → новое поле пароля → `Users.setPassword()`.

Пути «Восстановление доступа», кода восстановления и полного сброса в системе
нет — они убраны по требованию владельца. Если забыты и пароль, и код
владельца, запасного входа не остаётся: поможет только правка хранилища
браузера вручную.

Код владельца по умолчанию не задан: `DEFAULT_AUTH.code = null`. Владелец
задаёт его сам в панели администратора, вкладка «Питание». Хранится он
**отпечатком** (SHA-256 с солью и 12000 повторов), не открытым текстом. Учётные
записи — на вкладке «Пользователи».

Прочее:

- Верный ввод добавляет `toscreen` (карточка улетает в экран) и через 620 мс
  вызывает `showMonitor()`: монитор включается с `flash` (вспышка) и `zoom`.
- Клик по фону заблокированного экрана ставит курсор в поле пароля, а не пускает
  внутрь. Enter сам не пускает, пока пароль не введён.
- `#lockTitle` виден только при блокировке (правило `#lock.needcode .lock-title`).
- `restoreLockBody()` возвращает экран блокировки к обычному виду после того,
  как владелец ушёл в форму кода владельца и вернулся назад.

## Размер монитора

`.mon-screen` растянут на весь экран: `width:100%; height:100%; flex:1 1 auto`
внутри `#monitor` (`display:flex; flex-direction:column`). Рамка, «подбородок»
и подставка убраны из разметки — из-за них снизу оставалась полоса ~27 px.

Если снова появится полоса снизу, проверьте, что в `index.html` внутри
`#monitor` нет узлов-соседей у `.mon-screen`: любой лишний ребёнок отъедает
высоту, потому что контейнер флекс-колоночный.

## Адаптация: телефон, планшет, компьютер

Система работает на трёх размерах. Брейкпоинты в конце `styles.css`:

- `max-width:900px` — планшет и небольшой ноутбук;
- `max-width:760px` — колонка виджетов во всю ширину, боковая панель приложений скрыта;
- `max-width:560px` — телефон;
- `max-width:400px` — очень узкий телефон;
- `max-height:560px` — низкий экран (телефон в горизонтали);
- `hover:none` — сенсорный экран.

Что меняется на телефоне: высота панели задач берётся из `--tb-h` (56px против
52px), значки рабочего стола мельче, окна открываются во весь экран, ручки
изменения размера скрыты, меню Пуск и панели занимают всю ширину.

Правила, которые легко сломать:

- **Высота панели задач.** В `os.js` она читается из CSS-переменной `--tb-h`
  (`readTbH()`), а не задана числом. Не возвращайте константу: на телефоне
  панель выше, и окна начнут вылезать за низ.
- **Окна на телефоне.** При открытии (`WM.open`) окно получает `maximized: true`
  и класс `max`. При повороте экрана `WM.relayout()` пересчитывает все окна —
  он вызывается из `initResponsive()` по `resize` и `orientationchange`.
- **Сенсорное управление.** Перетаскивание и изменение размера висят на
  `pointerdown` (мышь и палец). Двойной тап по значку заменяет `dblclick`,
  долгое нажатие (520 мс) — правую кнопку. Наведение на сенсорных экранах
  сброшено блоком `@media (hover:none)`, иначе стиль залипает после тапа.
- **Поле кода на блокировке.** Внутренний блок `.lock-bottom > div` обязан
  тянуться на всю ширину (`width:100%`). Без этого поле считается от ширины
  текста и вылезает за экран на 320px.

## Имя пользователя

`USER` и `HOME` — изменяемые переменные в начале `os.js`. Их задаёт
`setCurrentUser(имя)` при входе: имя берётся из записи `Users`, а `HOME`
становится `C:\Users\<имя>`. Имя подставляется везде: разметка `data-sys="user"`,
ФС, пути Проводника, приглашение терминала, `whoami`, `neofetch`, почта и отчёт
администратора. Не вписывайте имя строкой — используйте `USER`, иначе оно
разъедется по путям.

Менять имя можно только через `setCurrentUser()`. Он же пишет `w12.lastuser`,
чтобы на экране входа подставить прошлую учётную запись. После входа
`applyCurrentUser()` пересчитывает домашнюю папку, рабочий стол и значки.

Рабочий стол у каждой учётной записи свой: `DESK_DIR` и `DESK_KEY` — изменяемые
переменные, их задаёт `setDeskScope()` (`DESK_KEY = 'lumen.deskItems.' + USER`).
Если добавите код, который читает `DESK_KEY` до входа, сначала вызовите
`setDeskScope()`.

Домашняя папка — `C:\Users\Степан`, узел дерева ФС задан как `[USER]`.
Домашняя папка создаётся в `loadDeskItems()`: `VFS.mkdir(HOME)`.

## Сервер и прокси

### Автозапуск после пересоздания контейнера

**Сейчас автозапуск не работает: платформа не вызывает хук.** Это проверено —
после пересоздания контейнера порты 12000 и 12001 оказались закрыты, хотя
`.openhands/setup.sh` на месте. Сам скрипт исправен: если запустить его руками,
сервер поднимается. Значит, дело не в скрипте, а в том, что эта версия
платформы хук не выполняет.

Что сделано в попытке починить. Точка входа — `.openhands/setup.sh` (штатный
хук OpenHands, по документации срабатывает при каждом старте работы с
репозиторием); он в фоне зовёт `autostart.sh`. Дубликаты: `setup.sh` в корне
проекта и `.openhands/setup.sh` в корне рабочей области `/workspace` — на случай,
когда платформа считает корнем не `/workspace/project`.

Почему только эти места. **Постоянный том в этом окружении ровно один —
`/workspace`.** Всё остальное (`/`, `/home/openhands`, `/etc`) при пересоздании
контейнера сбрасывается к образу. Попытка чинить автозапуск через `~/.bashrc`
и `/etc/profile.d/lumen-autostart.sh` провалилась именно поэтому: после
пересоздания хуки исчезали. Не переносите автозапуск в `$HOME`,
`/etc/profile.d`, `cron` или `systemd` — все они сбрасываются.

**Что делать при закрытых портах.** Поднять сервер вручную:

```bash
cd /workspace/project && ./serve.sh 12000 & ./serve.sh 12001 &
```

Надёжное решение — вынести автозапуск из контейнера наружу: держать проект на
GitHub (см. «Публикация на GitHub») и запускать его локально, где сервер
переживает перезапуск.

`autostart.sh` идемпотентен: проверяет порты 12000 и 12001 через `curl`,
берёт замок `/tmp/lumen-autostart.lock` (чтобы не поднять два сторожа) и
запускает `serve.sh` для каждого мёртвого порта.

Проверка автозапуска без перезагрузки контейнера:

```bash
cd /workspace/project
./serve.sh stop 12000; ./serve.sh stop 12001
rm -rf /tmp/lumen-autostart.lock
bash .openhands/setup.sh
sleep 10
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:12000/
```

### Запуск вручную

Запуск — `./serve.sh [порт]`, под капотом `python3 server.py`. Это не простой
`http.server`: помимо файлов проекта сервер отдаёт прокси `/__proxy?u=АДРЕС`.

Зачем прокси. Google, YouTube, Яндекс и другие сайты запрещают показ в рамке
заголовками `X-Frame-Options` и `frame-ancestors`. Обойти это в браузере нельзя.
Прокси делает иначе: сервер сам скачивает страницу, убирает запрещающие
заголовки и подставляет `<base>`, после чего отдаёт её как свою. Для рамки
страница становится своего источника, поэтому показывается.

Что делает сервер при проксировании:

1. Убирает из ответа `X-Frame-Options`, `Content-Security-Policy`, `HSTS`,
   `Cross-Origin-*`, `Permissions-Policy` и заголовки про сжатие.
2. Снимает `integrity` и `crossorigin` с тегов — через прокси они ломаются.
3. Вставляет `<base href="настоящий адрес">`, если у сайта своего `<base>` нет.
4. Вставляет скрипт-перехватчик: клики по ссылкам и отправка форм снова идут
   через прокси, поэтому навигация не выпадает из системы.
5. Пишет в страницу `<meta name="x-proxy-url">` — браузер читает из него
   настоящий адрес для строки адреса.
6. Ссылки вида `youtube.com/watch?v=...`, `youtu.be/...`, `shorts/...`
   переводит на плеер `youtube.com/embed/...` — плеер пускает в рамку.

Защита: прокси ходит только по `http` и `https` и не пускает на `localhost`,
`10.*`, `192.168.*`, `172.16-31.*`, `169.254.*`, `*.local` и подобные адреса.

Проверка прокси вручную:

    curl -s "http://localhost:12000/__proxy?u=$(python3 -c "import urllib.parse;print(urllib.parse.quote('https://www.google.com/'))")" | head -c 300

## Браузер

Приложение `browser` (`ICO.globe`). Работает в двух режимах, выбор — по наличию
сервера.

**Живой режим (основной).** Сервер поднимает настоящий Chromium и отдаёт его
экран в окно через `/__live` (WebSocket). Мышь и клавиатура уходят обратно в
Chromium, поэтому для сайта это обычный браузер: работают поиск, вход в
аккаунты и видео. Если сервер не запущен, окно пишет об этом и переходит в
простой режим.

**Простой режим.** Страницы грузятся через серверный прокси `/__proxy`.
Показывает только простые страницы: сайты на JavaScript не оживают. Ссылка на
ролик YouTube переводится на плеер, но YouTube проверяет источник запроса и
отдаёт «Видео недоступно» (код 152).

Начальной страницы отдельным файлом нет: кнопка «домой» ведёт на Google, а
десять быстрых закладок перечислены в `os.js` (`QUICK`). Из другого места
системы браузер открывается вызовом `rec.api.open(url)`.

Проверка прокси вручную:

    curl -s "http://localhost:12000/__proxy?u=$(python3 -c "import urllib.parse;print(urllib.parse.quote('https://www.google.com/'))")" | head -c 300

Что проверено вживую в простом режиме:

- Google: главная открывается. Поиск иногда показывает проверку «подозрительный
  трафик» — запросы идут с серверного адреса. Это ограничение Google.
- Википедия, Викисклад, Архив интернета, проект «Гутенберг», example.com,
  news.ycombinator.com, vk.com: открываются нормально.

Вывод: прокси обычный браузер не заменяет — для этого и сделан живой режим.

## Игры

Приложение `games` (`ICO.game`). Пять игр в одном окне, переключаются чипами:
Змейка, Тетрис, Понг, Арканоид, 2048. Рекорды лежат в localStorage под ключами
`lumen.snake.best`, `lumen.tetris.best`, `lumen.pong.best`, `lumen.ark.best`,
`lumen.g2048.best`.

Управление сделано так, чтобы играть можно было одной мышью. Под полем есть
панель `.g-pad` с кнопками; для стрелок удержание повторяет нажатие. Клавиатура
тоже работает.

Каждая игра — объект с `init(host)`, возвращающий `{frame, key, keyup, restart,
help}`. Свойство `pad` задаёт кнопки на экране. `frame(dt)` вызывается через
`requestAnimationFrame`, `key(k)` — из обработчика `keydown`. Счёт игра отдаёт
событием `gscore` на узле-хосте, подписка одна — в `start()`.

Важно: игра рисуется, только когда её окно активное (`State.active === rec.id`).
Иначе пять игр с `requestAnimationFrame` грузят процессор и система тормозит.

Клавиши система отдаёт активному окну через `rec.api.keys`, и это делается до
обработки Win-сочетаний и до переключения окон стрелками. Если добавить игру со
своими клавишами, достаточно вернуть `true` из `key`.

Запуск конкретной игры: `WM.open('games', 'Понг')`. Повторный запуск с
аргументом переиспользует уже открытое окно. Файлы `*.exe` с `ext: 'game'` в
папке `C:\Users\Степан\Игры` запускают игру двойным кликом из Проводника.

## Публикация на GitHub

Проект выкладывается в `stepankazacuk-png/win12_lumen`. Ветка — `main`.

**Автоматический доступ в этом окружении только на чтение.** Токен опознаётся
как `stepankazacuk-png`, репозитории видит, но любую запись отклоняет: `git push`
возвращает `403`, `POST /user/repos` — `Resource not accessible by integration`.
Проверено и через `git`, и через `gh`, и через REST. Заливать нужно токеном
владельца с правом «repo» — для этого есть `push-to-github.sh`:

```bash
GITHUB_TOKEN=ваш_токен ./push-to-github.sh
```

**Тонкий момент про fine-grained токен.** У него права раздаются по разделам, и
«Contents» по умолчанию только на чтение. Симптом обманчив: токен успешно
создаёт репозитории (`POST /user/repos` → `201`), создаёт issues (`201`), читает
файлы, но `git push` падает с `403 Permission ... denied`, а
`PUT /contents/файл` отвечает `Resource not accessible by personal access token`.
Ответ сервера прямо называет, чего не хватает — заголовок
`x-accepted-github-permissions: contents=write`.

Что включить в токене, чтобы заливка прошла:

| Раздел | Право | Зачем |
| --- | --- | --- |
| Contents | Read and write | `git push`, запись файлов |
| Administration | Read and write | включить Pages, менять описание |
| Pages | Read and write | публикация сайта |
| Issues | Read and write | создавать и закрывать задачи |

Классический токен с одним правом «repo» закрывает всё сразу. Выдавайте
минимально нужный набор и отзывайте токен после заливки: он даёт полный доступ
к репозиторию.

Скрипт передаёт токен прямо в команду `git push` и в конфиг его не пишет.
Проверяйте, что токена нет в `.git/config`: `grep -c 'gh[up]_' .git/config`.

### Чистка истории от кодов и паролей

Раньше в исходниках лежали код владельца и пароль учётной записи, и они попали
в историю Git — то есть были видны на GitHub в каждом старом коммите, в архиве
релиза и на живом сайте. Отпечатки в `w12.auth` проблему не решали: открытый
текст оставался в прошлых коммитах.

История переписана через `git filter-repo`:

```bash
pip install git-filter-repo
# в файле замен — сами секреты и их замена, по одной паре на строку:
#   <старый код>==>XXXXXX
#   <старый пароль>==>XXXXXX
git filter-repo --replace-text /tmp/replace-secrets.txt \
                --replace-message /tmp/replace-secrets.txt --force
git reflog expire --expire=now --all && git gc --prune=now --aggressive
```

`--replace-text` чистит файлы в каждом коммите, `--replace-message` — сообщения
коммитов (секрет был и там). После этого в истории ноль вхождений; проверяется
так:

```bash
git rev-list --all | while read c; do git grep -l '<старый код>\|<старый пароль>' $c; done
```

Команда `filter-repo` удаляет `origin` — это защита от случайной отправки.
Добавьте его обратно вручную.

**Перезапись истории меняет все хеши.** Обычная отправка после неё отклоняется:
новые коммиты в родстве со старыми не состоят. Нужен `FORCE=1`:

```bash
GITHUB_TOKEN=ваш_токен FORCE=1 ./push-to-github.sh
```

Скрипт в этом режиме ещё и пересобирает релиз `v1.0`: в старом архиве лежали
прежние исходники с кодами. Релиз удаляется вместе с тегом и создаётся заново
из чистого `lumen.zip` — тег при этом ставится на текущий `main`, иначе релиз
указывал бы на старый коммит.

Порядок важен: сначала перезапись и чистка, потом `FORCE=1`-заливка. Если
залить раньше, старые коммиты вернутся на GitHub.

**Что остаётся сделать владельцу.** В этом окружении токен только на чтение,
поэтому отправка невозможна — ни обычная, ни с `--force`. Пока она не сделана,
прежний код владельца и пароль учётной записи по-прежнему открыты:

- в истории коммитов `main` на GitHub;
- в архиве релиза `v1.0`;
- на сайте GitHub Pages (там лежит старый `os.js`).

Нужен токен с правом «Contents: Read and write» и один запуск
`FORCE=1 ./push-to-github.sh`. После него проверить: в старых коммитах секретов
нет, релиз содержит новый архив, сайт отдаёт `os.js` без констант.

Заодно смените сам код и пароль: раз они лежали в открытом доступе, считать их
секретными уже нельзя. После заливки задайте новый код владельца при первом
запуске — старый в отпечатках не сохранится. Пароль учётной записи задаётся
отдельно: в панели администратора, вкладка «Пользователи».

### Сайт на GitHub Pages

Сайт включён и работает: <https://stepankazacuk-png.github.io/win12_lumen/>.
Источник — ветка `main`, папка `/ (root)`, сборки нет: система статические
файлы. Включается один раз: Settings → Pages → Source → «Deploy from a
branch» → Branch `main`, папка `/ (root)`.

**Почему не через Actions.** Первый вариант — workflow
`.github/workflows/pages.yml` — не залился: GitHub отвечает
`refusing to allow a Personal Access Token to create or update workflow
.github/workflows/pages.yml without workflow scope`. Классическому токену с
правом `repo` не хватает отдельного права `workflow`, а fine-grained токену —
раздела «Workflows». Публикация из ветки делает то же самое и не требует ни
права `workflow`, ни служебных файлов. Если такой workflow понадобится,
заливать его придётся токеном с правом `workflow`.

**Файл workflow нельзя просто удалить коммитом.** GitHub отклоняет push, если
`.github/workflows/*` встречается в *любом* отправляемом коммите, даже в том,
где файл удалён. История вычищена так:

```bash
git filter-branch -f --index-filter \
  'git rm --cached --ignore-unmatch -r .github' --prune-empty HEAD
git branch -D backup-before-clean; rm -rf .git/refs/original
git reflog expire --expire=now --all && git gc --prune=now
```

Проверка, что не осталось следов: `git rev-list --all --objects | grep -c .github`
должно вернуть `0`.

Публикуются все файлы из корня, но нужны только `index.html`, `styles.css`,
`os.js` и `.nojekyll` (последний — чтобы Jekyll не трогал файлы). `server.py`
на Pages бесполезен (нет Python), а встроенному браузеру всё равно нужен свой
сервер — без него окно пишет «Сервер не запущен. Откройте систему через
server.py». Остальное работает полностью: включение, вход по коду, рабочий
стол, окна, терминал, проводник, блокнот, калькулятор, игры, музыка, настройки.
